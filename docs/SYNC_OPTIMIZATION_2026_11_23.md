# Aisora: первая безопасная оптимизация синхронизации

**Ветка:** только `main`. **Сохранённая рабочая точка:** `aisora-working-local-cc7f5b7`. **Режим работы:** локальный Telegram-бот на Mac + существующий Playwright + PostgreSQL/Redis. Облачный запуск не требуется.

## Основание: реальные данные за 23.11.2026

- 5 396 действий Playwright, 623 диагностических события; 8 дисциплин.
- 40 безрезультатных ожиданий условий задания по 8 секунд.
- 8 безрезультатных ожиданий содержимого отправленных сообщений по 60 секунд.
- 134 ожидания недели по ~3 секунды.
- 57 МБ `trace.zip`, большой промежуток после последней операции; теперь `browserElapsedMs` и `traceStopMs` измеряются отдельно.
- Успешные `waitForFunction` завершались максимум примерно за 1.2 секунды в представленной трассе. Это основание для контролируемого ограничения ожиданий; **не гарантия на других запусках**.

## Что изменено в первой итерации

1. **Кэш отправленных сообщений в пределах одного `/sync`.** Aisora по-прежнему получает таблицу «Отправленные» для каждой дисциплины, но повторно не открывает один и тот же успешно прочитанный документ/сообщение. Ключ учитывает ID, дату и тему. Ошибочный просмотр не повторяет минутное ожидание для каждой дисциплины; результат помечается неполным.
2. **Ограничение ожиданий без доказательств нового содержимого.** По умолчанию не более 10 секунд для непоменявшегося тела сообщения, 4 секунд для непоменявшейся карточки задания (и не дольше старых настроенных максимумов). При сомнении не подставляется старое содержимое другого задания. Отключается через `AIS_SYNC_ADAPTIVE_TIMEOUTS=false`.
3. **Различие между `ABSENT` и `UNKNOWN`.** Если чтение отправленных сообщений неполное, отсутствие найденного соответствия не означает, что работа не отправлена. Предыдущее подтверждение сохраняется при новом результате `UNKNOWN`.
4. **Защита PostgreSQL.** Старая запись CONTENT удаляется только если текущая неделя **явно полностью проверена**: правильный видимый заголовок, есть соответствующий контент, все запрошенные подробности прочитаны. В противном случае ранее известные задания и текст сохраняются, даже если АИС временно вернула пустой ответ. СРО, ранее подтверждённое как отправленное, тоже не становится «не отправлено» лишь из-за отсутствия свежего доказательства.
5. **Безопасная проверка текущей недели.** Подсветка кнопки недели без совпадающего заголовка уже не считается успешным завершением AJAX. Если заголовок отсутствует, прежняя пауза сохраняется, а такая неделя не разрешает удаление старого содержимого.
6. **Лёгкая диагностика.** Новые поля `browserElapsedMs` и `traceStopMs`. Можно записывать `report.json` без тяжёлых приватных снимков `trace.zip`.

## Настройки в существующем .env

Для **первого контрольного запуска** (без полной трассы):

```dotenv
AIS_SYNC_DIAGNOSTICS_ENABLED=true
AIS_SYNC_TRACE_ENABLED=false
AIS_SYNC_ADAPTIVE_TIMEOUTS=true
AIS_MESSAGE_STALE_WAIT_MAX_MS=10000
AIS_DETAIL_STALE_WAIT_MAX_MS=4000
AIS_ADAPTIVE_WEEK_WAIT=false
```

Оставить прежние `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, `REDIS_URL`, `CREDENTIALS_MASTER_KEY`, `AIS_BROWSER_HEADLESS`, `AIS_AUTOMATION_APPROVED` как есть.

**Не включать `AIS_ADAPTIVE_WEEK_WAIT=true` в первом контрольном запуске.** Это экспериментальное сокращение ожидания 3 секунд до 350 мс только когда АИС явно показывает верную неделю. Для него нужна отдельная проверка на реальных страницах, чтобы не пропускать СРО/СРСП.

## Проверка на Mac

Остановить локальный сервер и из папки Aisora:

```bash
git status
git pull --ff-only origin main
pnpm typecheck
pnpm test
pnpm build
```

Если команды показывают ошибки, **не запускай новую синхронизацию**: пришли вывод. Не запускай `git reset --hard` и не переписывай `.env`.

После успешных проверок:

```bash
pnpm start:dev
```

Затем `/sync` в **старом** Telegram-боте. По завершении:

```bash
node scripts/last-sync-diagnostics.cjs
```

Отправить в чат **только** `report.json` и текстовую сводку; полную трассу и приватное содержимое АИС не публиковать.

Сравнивать: число дисциплин, СРО/СРСП/лаб, оценки, подтверждённые отправки, старые подробные условия задания, число `UNKNOWN`, число тайм-аутов, время `browserElapsedMs`, время `traceStopMs`. Не считать ускорение успешным, если часть правильных данных потеряна.

## Что намеренно отложено

- Удаление повторных переходов к одной и той же неделе (92 случая) — сначала нужен контрольный запуск: при неверном предположении о состоянии AJAX можно перепутать задания разных недель.
- Автоматический поиск заданий в силлабусе Word, если карточка СРО есть, а задания в журнале нет — отдельное последующее требование.
- Самообучение и ИИ-модель — не входят в оптимизацию.
- Изменение базы данных, перенастройка токенов Telegram, перевод на облачный сервер — не требуются.

**Ожидаемое улучшение** нельзя считать гарантированным до нового `/sync`; первая итерация устраняет самые дорогие повторные и неподтверждённые ожидания, сохраняя безопасный откат по флагам.
